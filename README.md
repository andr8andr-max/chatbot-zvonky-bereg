# Чат-бот «Звонкий берег» · Ирина

Бот сообщества ВКонтакте: отвечает на вопросы о фестивале, проводит анкету,
регистрирует заявку с номером, показывает статус и уведомляет организаторов.

Ничего ставить не нужно, кроме Python 3.11+ (проверено на 3.14). Google
таблица — необязательна, без неё заявки пишутся в SQLite и CSV.

---

## 1. Куда добавлять ключи

**Все секреты — только в файл `.env` в корне проекта.** Он создаётся один раз
из шаблона и никогда не коммитится в git (уже добавлен в `.gitignore`).

```powershell
Copy-Item .env.example .env
notepad .env
```

Заполнить нужно **два** значения:

| Что | Переменная | Где взять |
|---|---|---|
| **Токен сообщества ВК** | `VK_GROUP_TOKEN` | Сообщество → Управление → Дополнительно → Работа с API → Ключи доступа → создать ключ → **включить доступ к сообщениям** |
| **Ключ Proxy API** | `LLM_API_KEY` | [proxyapi.ru](https://proxyapi.ru) → личный кабинет → Ключи API → создать (начинается с `sk-`, показывается один раз) |

Обязательно также заполнить без секретов:

| Переменная | Что это | Как узнать |
|---|---|---|
| `VK_GROUP_ID` | ID сообщества, **число без минуса** | адрес `vk.com/club123456789012` → `123456789012` |
| `VK_ADMIN_USER_IDS` | ваш ID, чтобы работали команды `!статус` | профиль → «Свойства» поля `id` |
| `VK_ADMIN_PEER_IDS` | ID бесед для уведомлений организаторам | беседа → ⋮ → «Информация» → «Идентификатор беседы» |
| `VK_ADMIN_USER_IDS` | ID организаторов, кому бот пишет в личку как запасной канал | профиль → «Свойства» поля `id` |

В `VK_ADMIN_PEER_IDS` — **только беседы**. Личные чаты туда добавлять нельзя:
организатор получит одно уведомление и в беседу, и в личку, и в личку, и решит,
что бот сошёл с ума. Лички бот и так использует сам, когда беседа недоступна
или случай срочный. Если в списке окажется личный чат, `check` об этом скажет.

Подробная расшифровка каждой строки — в комментариях внутри `.env.example`.

> **Токен пользователя использовать нельзя.** Нужен именно community token
> сообщества — иначе нарушение правил VK и риск блокировки.
> Если `VK_GROUP_TOKEN` выглядит короче ~40 символов, бот предупредит при старте.

## 2. Проверка, что всё настроено

```powershell
.\run.ps1 check      # конфигурация, секреты, безопасность — без сети
.\run.ps1 diag       # плюс проверка Proxy API, Long Poll и Google (нужны ключи)
.\run.ps1 test       # 437 автотестов, сеть не используется
```

`check` скажет, если чего-то не хватает. `diag` делает реальные запросы и
покажет, доступен ли ключ Proxy API и Long Poll.

## 3. Запуск

```powershell
.\run.ps1            # или .\run.ps1 run — запустить бота
```

Бот работает, пока открыто окно. Остановить — `Ctrl+C`. Для фоновой работы
на Windows используйте планировщик задач, для Linux — systemd.

Логи: `data/bot.log`. База: `data/bot.sqlite3`.

### Проверка сценариев и отправка уведомлений

Проверить, что уведомления вообще доходят, можно одной командой:

```
python -m bot notify
```

Она отправляет сообщение, помеченное «🧪 ТЕСТОВОЕ УВЕДОМЛЕНИЕ», и идёт через
тот же путь отправки, что и настоящие заявки, так что проверяется вся цепочка
сразу. Свой текст: `python -m bot notify "проверка"`.

Куда дойдёт уведомление: сначала в беседы из `VK_ADMIN_PEER_IDS`. Если хотя бы в
одну дошло — **в лички из `VK_ADMIN_USER_IDS` ничего не отправляется**, чтобы
организаторы не читали одно и то же трижды. В лички уходит только если беседа
недоступна сообществу (ошибка 917) или беседы не заданы. Исключение — срочное
оповещение («ЭКСТРЕННАЯ СИТУАЦИЯ»): оно всегда идёт и в беседу, и в лички.

### Убрать заявку, созданную при проверке

```
python -m bot del ЗБ-0001          # показать, что найдётся, и не удалять
python -m bot del ЗБ-0001 --yes    # удалить
```

Команда удаляет заявку из базы и из CSV-выгрузки и **подтягивает нумерацию**:
счётчик номеров сам не уменьшается, поэтому после удаления последней заявки
следующая получила бы `ЗБ-0002`, и в нумерации появился бы пропуск.

Номер в середине не переиспользуется: удалили `ЗБ-0002` при наличии `ЗБ-0003` —
следующей будет `ЗБ-0004`, иначе один номер достался бы двум заявкам.

**Исключение — экстренные оповещения:** они всегда идут и в беседу, и в лички,
даже если беседа работает. Беседу организаторы могут не смотреть часами, а в
личке человек увидит сразу.

Что произошло, видно в `data/bot.log`: «доставлено в беседу», «Экстренное
уведомление доставлено в беседу … и в лички …» или «беседа недоступна,
доставлено в лички».

В `.env` есть `DRY_RUN`:

```
DRY_RUN=1
```

В этом режиме бот **не отправляет уведомления организаторам** (ни в беседу, ни в
лички; в лог и аудит пишется, что отправка была), а посетителю отвечает как обычно.
Нужен, чтобы при проверке эскалации или ЧП в боевом сообществе никто не получил
«ЭКСТРЕННАЯ СИТУАЦИЯ» по-настоящему. При старте с этим режимом бот пишет в лог
предупреждение, а `python -m bot check` показывает его в строке «Режим отправки».
Не забудьте вернуть `DRY_RUN=0`.

## 4. Google Таблица (по желанию, но нужно для сценария с куратором)

1. Создайте таблицу и включите Google Sheets API в Google Cloud.
2. Создайте сервисный аккаунт, скачайте JSON-ключ **вне папки проекта**.
3. Откройте таблицу на доступ этому сервис-аккаунту (ссылка → редактор).
4. Впишите в `.env`:
   ```
   SHEETS_ENABLED=true
   GOOGLE_SPREADSHEET_ID=1AbCdEf…   (из адреса таблицы)
   GOOGLE_CREDENTIALS_FILE=C:\путь\к\файлу\service-account.json
   ```
5. Установите библиотеки: `python -m pip install -r requirements-sheets.txt`
6. Проверьте связь одной командой: `python -m bot sheets-test`

`python -m bot sheets-test` проверяет всё по шагам и печатает, что именно
не так: установлены ли библиотеки, не остался ли ID из `.env.example`
(он выглядит как `1AbCdEfGhIjKlMnOp0000…` и не пройдёт проверку), найден ли
файл ключа, есть ли доступ к таблице и **работает ли именно запись** — она
пишет пробу во временную ячейку, читает её обратно и очищает, потому что
права «Читатель» выглядят как рабочие, пока не попробуешь записать.

Пока ключа и ID нет, заявки не теряются: бот пишет их в SQLite и в
`data/applications_export.csv`, а организаторам уходит предупреждение.

Листы и заголовки создаются сами при первой заявке — по одной таблице на
категорию (`Музыканты_Группы`, `Художники_Мастера`, `Фудкорт`, `Волонтёры`).
Колонки фиксированы и перечислены в `bot/sheets.py:HEADERS`; позиции статуса
и комментария берутся оттуда, а не пишутся числами.

**Куратор меняет статус двумя способами — оба работают:**

- **Правкой ячейки** в колонке «Статус». Бот читает таблицу каждые
  `SHEETS_POLL_INTERVAL_SEC` секунд и сам пишет участнику. Это основной путь.
- **Командой в чате**: `!статус ЗБ-0001 Одобрена` (работает и без таблицы).

Статусы: `Новая`, `На рассмотрении`, `Одобрена`, `Отклонена`, `Нужен ответ`.
Комментарий добавляется после статуса: `!статус ЗБ-0001 Нужен ответ уточни райдер`.

Без таблицы заявки всё равно не теряются: SQLite + `data/applications_export.csv`.

### Вопрос организатору: как вернуть ответ

Вопрос уходит организаторам с меткой `[вопрос N]`, а человек видит кнопку
«Отменить вопрос». Ответить можно двумя способами — оба возвращают текст
человеку в тот же чат, где он спросил, снимают кнопку и снимают ожидание:

- **Ответить на сообщение бота** с вопросом — обычный способ.
  Бот узнаёт вопрос по метке `[вопрос N]` в тексте сообщения, на которое
  ответили. Это основной путь: при отправке в беседу VK отдаёт вместо номера
  сообщения ноль, так что сверить ответ по id в беседе невозможно (проверено
  на живом API). По id бот всё же ищет — на случай личной переписки.
- **Написать `!ответ N текст`**, где `N` — номер из метки. Нужно, если
  вопросов много или организатор пишет не «в ответ», а отдельным сообщением.

**Отвечать можно из бесед.** VK не отдаёт сообществу в Long Poll сообщения,
написанные **от его имени**: в объекте сообщения это `from_id = -группа`,
`out = 1`, а человек-автор лежит в поле `admin_author_id`. В чате такая реплика
неотличима от сообщения бота, поэтому бот:

- считает `admin_author_id` автором, а не «своим» сообщением
  (`bot/vk_api.py`, `parse_message_event`; `bot/app.py`, `_is_own_event`);
- помимо Long Poll каждые 12 секунд опрашивает `messages.getHistory` по
  беседам из `VK_ADMIN_PEER_IDS` и обрабатывает новые сообщения оттуда
  (`Application._poll_chats`). При первом опросе запоминается текущий край
  истории, чтобы после перезапуска бот не отвечал на старые вопросы.

Беседа, в которой сообщество не состоит, истории не отдаёт: в этом случае
poller помечает её недоступной, а беседа продолжает работать через Long Poll.
В беседу добавляется **бот сообщества**, а не сообщество целиком, — если бот
уже добавлен, `messages.getHistory` может всё равно вернуть ошибку 15, и это
не чинится настройкой. Рабочий способ ответа в такой беседе — ответить
напрямую на сообщение бота.

Если сообщения из бесед не приходят, в логе есть строка `Long Poll жив: N
опросов подряд без событий` — это отличает «бот молчит» от «цикл встал».

Ответ организатора разбирается **до** фильтра «отвечать только на упоминания»,
иначе в беседе он отбрасывался как обычная реплика, и человек оставался без
ответа. Оба способа работают без обращения к боту — достаточно ответить «в
ответ» или написать команду.

После ответа бот пишет подтверждение `✅ Вопрос №N закрыт`, чтобы остальные
организаторы не ответили на тот же вопрос повторно. Если VK это подтверждение
не примет, участник всё равно получит ответ: сбой подтверждения не отменяет
уже отправленный ответ.

**В личных чатах бот реагирует только на собеседника.** Реплики организатора,
написанные от имени сообщества (`from_id = -группа`, `admin_author_id = человек`),
в личке игнорируются: это не сообщение участника, и отвечать на него нельзя.
В беседах такие реплики, наоборот, обрабатываются — в них ответ организатора
(`bot/app.py`, `_on_event`).

Кнопка «Отменить вопрос» гасит **сам вопрос**, а не только ожидание, и
уведомляет организаторов, что отвечать не нужно. Без этого организаторам
приходилось отвечать тому, кто ответа уже не ждёт.

### Одна заявка с аккаунта

Заявка принимается **один раз с аккаунта**, категория значения не имеет.
Повторная подача блокируется на трёх уровнях:

- в боте — при выборе категории и при простой кнопке «Подать заявку»;
- в `DuplicateApplication` — при сохранении, даже если обойти проверки бота;
- в SQLite — частичный уникальный индекс `ux_app_live` по `user_id`, поэтому
  две живые заявки невозможны на уровне базы.

Отклонённая заявка не считается живой: после неё можно подать новую.
Проверка по телефону работает отдельно и включается вместе с
`STORE_PII_LOCALLY=true`: она предупреждает, что этот номер уже встречался
в заявке другого аккаунта, и требует подтверждения.

### Необязательные поля анкеты

Поля «Ссылка» и «Фото / файл» можно пропустить: текстом («пропустить»,
«пропустим», «дальше», «нет», «не хочу») или кнопкой «Пропустить», если она
есть. После двух подряд невалидных ответов на необязательное поле бот сам
оставляет его пустым и идёт дальше («Ладно, этот пункт оставим пустым 🙂»).

Вопрос об имени учитывает категорию: волонтёру — только «Как вас зовут?»,
исполнителю/мастеру — «Как вас зовут? Если у вас группа или проект —
напишите название.»

### Редактирование заявки перед отправкой

На сводке поля пронумерованы (1–8), чтобы человек мог поправить конкретное
значение. Правка принимается номером поля («4»), названием («почта») или
синонимом («e-mail», «телефон», «город»). После одного изменённого поля бот
сразу возвращает к сводке, не переспрашивая остальные.

## 5. Персональные данные

`STORE_PII_LOCALLY` в `.env`:

- `true` (по умолчанию) — телефон и почта лежат в SQLite. Нужно для истории
  заявок и офлайн-уведомлений. **Файл базы содержит персональные данные.**
- `false` — в SQLite остаётся только необратимый хеш телефона (поиск дублей
  работает), а реальные контакты уходят в Google Таблицу и организатору.

Контакты не дублируются в переписке: при возврате на шаг назад бот
показывает замаскированное значение (`+7 *** ***-45-67`). Подробнее — в
`SECURITY.md`.

## 6. Структура

```
bot/
  config.py     настройки из .env, самопроверка безопасности
  security.py   валидация полей, маскирование, антифлуд, редакция секретов
  storage.py    SQLite: заявки, статусы, состояния диалога, миграции
  flows.py      конечный автомат: меню, анкета, статус, вопрос организатору
  prompts.py    сборка системного промпта и истории для модели
  llm.py        клиент Proxy API (ling-3.0-flash)
  vk_api.py     VK API, Long Poll, разбор событий
  keyboards.py  кнопки VK с белым списком действий
  typing.py     системный индикатор «печатает…» (messages.setActivity) на время ответа модели
  sheets.py     Google Sheets (опционально) и CSV-запасной вариант
  app.py        цикл Long Poll, опрос таблицы, напоминания
  __main__.py   команды запуска: run, check, diag, test-message,
                notify, chats, watch-chat
tests/test_bot.py   437 тестов, сеть не нужна
```

Промпт, характер и база знаний лежат отдельно и правятся без изменения кода:
`SYSTEM_PROMPT_Irina_Zvonky_Bereg.md`, `Irina_Character.md`,
`Zvonky_Bereg_Knowledge_Base.md`. Путь к характеру переопределяется
переменной `CHARACTER_FILE`; если файла нет, бот работает как раньше.
В `Irina_Character.md` — тон и стандарты поведения Ирины: спокойная
уверенность, ориентация на решение, уважение, эмпатия.

Файл характера — только про тон, без технических ограничений и без
сценариев. Раньше там было «бот не должен имитировать личность», запрет на
живые обороты вроде «я тут», примеры на «ты» для волонтёров и ссылки на
сайт: всё это либо спорило с остальным промптом, либо модель переносила в
ответы участникам. Сейчас примеры адресованы участникам, обращение только
на «вы», а ограничения лежат в блоке `RUNTIME_RULES`.

## 6.1. Как собирается системный промпт

Порядок блоков в `bot/prompts.py` задан не случайно:

1. `RUNTIME_RULES` — технические ограничения: «вы», без ссылок, без выдумок,
   без обещаний, приветствие только в начале общения;
2. `Irina_Character.md` — тон и привычки;
3. базовый промпт — persona, факты о фестивале, сценарии, примеры;
4. `CLOSING_REMINDER` — короткое повторение главного в самом конце.

Модель хуже всего держит конец длинного промпта, поэтому критичные правила
уходят в начало, а напоминание закрывает хвост.

Раньше все сообщения обрезались до 20 000 символов, и системный промпт
переставал на середине: правила и характер до модели не доходили вовсе —
правки промпта не давали эффекта. Теперь ввод участника режется до
`USER_MAX_LEN` (20 000), а системный промпт — до `SYSTEM_MAX_LEN`
(120 000). Собранный промпт — около 38 000 символов, живой ответ — 2–5 с.

Проверяется тестами `TestPromptIntegrity`: лимиты не режут инструкции,
порядок блоков не разъезжается, в примерах ответов нет адресов.

## 6.2. Ссылки вырезаются кодом, а не только запретом в промпте

Запрет в промпте модель соблюдает не всегда: один и тот же вопрос про
парковку то уходил с адресом, то без. Поэтому `strip_links()` в
`bot/flows.py` убирает адреса из ответа модели принудительно, после
`_guard_facts`.

Защищены не только `example.com`, но и мессенджеры с путями — именно они
доезжали до участников: `t.me/zvbereg`, `vk.com/zv_bereg`, `wa.me/…`,
`discord.gg/…`, `ok.ru/…`. Голые домены и почта тоже вырезаются.

Ответы организаторам из админки фильтр не трогает: там организаторам нужны
рабочие ссылки на переписку.

## 7. Сколько бот ждёт модель

`ling-3.0-flash` — reasoning-модель: она может думать долго, а на
непонятном вводе (например, сообщение, набранное в английской раскладке)
думает так долго, что ответ не помещается в `LLM_MAX_TOKENS` и приходит
пустым. Проверено на живом API: на вопрос «сколько стоит вход?» уходило
20 секунд с пустым ответом, а человек всё это время смотрел на индикатор
«печатает…».

Поэтому время ограничено сверху, а не увеличено:

- `LLM_TIMEOUT` (12 с) — таймаут одного запроса к модели;
- `LLM_BUDGET_SEC` (15 с) — общий лимит на **все** запросы в одном
  сообщении: определить намерение и сгенерировать ответ. Из него же
  оплачиваются паузы перед повторами.

Что происходит при превышении: запрос не отправляется вовсе, повтор не
делается, бот сразу отвечает шаблоном и предлагает «Вопрос организатору».
В лог при этом пишется причина с числами — сколько ждали и какой лимит:

```
Бюджет времени на ответ исчерпан, повтор не делаю: время на ответ истекло: ждали 15 с, лимит 15 с
```

`python -m bot check` предупредит, если `LLM_TIMEOUT` больше
`LLM_BUDGET_SEC` (таймаут не сработает) или бюджет больше 45 с (человек
столько не ждёт).

`LLM_MAX_TOKENS` (1500) — верхняя граница ответа, а не плата: модель
расходует столько токенов, сколько реально написала, а живой замер даёт
157–331 токен на ответ. Поэтому лимит спокойно подняли с 500 — на сложном
вопросе reasoning-модель успевала потратить 500 токен на размышление и
вернуть пустоту, и участник получал отказ вместо ответа.

Пустой ответ из-за лимита теперь отличим от сбоя: если модель закончила по
длине (`finish_reason == "length"`), `bot/llm.py` повторяет запрос **один
раз** с вдвое большим бюджетом (1500 → 3000) и только затем отвечает
шаблоном.

Один повтор — осознанный компромисс. Три повтора до 4000 в худшем случае
съедали 8500 токенов и все 15 с ожидания на одно сообщение, а при лимите
1500 обрезка по длине и так стала редкой: если и 3000 токенов не хватило,
второй повтор уже не окупается. Повтор по обрезке не отнимает сетевые
попытки: счётчики в `bot/llm.py` раздельные.

## 8. От чьих сообщений бот отвечает в личке

В личной переписке бот отвечает **только на сообщения собеседника**.
Реплику, написанную от имени сообщества, он не трогает.

Признак «от имени сообщества» — поле `admin_author_id`, и **знак `from_id`
туда не входит**. Это и было причиной, по которой фильтр не работал: VK
отдаёт одно и то же по-разному.

| что сделал организатор | `type` | `from_id` | `out` | `admin_author_id` |
|---|---|---|---|---|
| написал от себя | `message_new` | `+62568203` | `0` | нет |
| написал от имени сообщества | `message_reply` | `+62568203` | `1` | `62568203` |
| то же в беседе | `message_new` | `-241767034` | `1` | `62568203` |

В беседе `from_id` отрицательный, в личке — **положительный**. Проверка
`from_id == -группа` в личке не срабатывала никогда, и бот отвечал на
сообщение сообщества. Разбор события переписывает `from_id` на
автора-человека, поэтому признак запоминается до перезаписи и хранится в
`Message.from_community`.

Две ловушки, обе закрыты тестами:

- **`peer_id == from_id` — не признак «своих заметок».** В переписке
  пользователя с сообществом `peer_id` тоже равен его `from_id`. Правило
  отсекло бы весь диалог с каждым посетителем.
- События в личке пишутся в лог целиком (`Сырое событие ... в личке:`).
  Обрезать нельзя: `admin_author_id` стоит в хвосте `object`, и на первых
  600 символах признак терялся — баг с личкой невозможно было увидеть.

## 9. Бессмысленный ввод: почему он не доходит до модели

Время можно обрезать сверху, но дешевле вообще не тратить его зря. Мусор и
забытая раскладка отсекаются локально, до обращения к модели
(`bot/security.py`, `is_meaningless`, `reads_as_russian`; вызов — в
`BotEngine._free_dialog`).

Проверено замером: сообщение `Gbie jn bvtyb cjj,otcndf` (русский текст в
английской раскладке) съедало **15,5 с и все 400 токенов** классификатора,
не дав ответа. Теперь тот же ввод обрабатывается за **1–4 мс и 0 токенов**.

Два разных случая, и это важно:

- **Мусор** — «ыыы», «фывапр», «asdasd», «бгдщ», «qwerty», а также ввод без
  букв и цифр: «))))», «---», «🙂🙂». Признаки: повтор одной буквы, пробег по
  клавиатурному ряду, чередование двух-трёх символов, слово без гласных, нет ни
  одной буквы или цифры. Бот отвечает «похоже, получилось случайным» и
  предлагает кнопки. Токены не тратятся.
- **Забытая раскладка** — это не мусор, а настоящий русский вопрос, просто
  набранный в чужой раскладке. Отказывать нельзя, поэтому бот переводит
  текст и показывает, как понял: «Я прочитала так: «Пишу от имени
  сообщества»». Человек подтверждает и получает ответ. Токены тоже не
  тратятся.

Настоящая латиница (`hello world`, `Instagram`, `Telegram`, `VKontakte`)
забытой раскладкой не считается: перевод даёт «реддщ щрдщ», и проверка
узнаёт это по отсутствию знакомых слов.

Ложное срабатывание опаснее промаха — заблокировать настоящий вопрос хуже,
чем один раз потратить токены, поэтому критерии строгие:

- короткие слова не трогаем: «ок», «да», «фф», «ыы»;
- цифры пропускаем: «5», «5/5», «+7 916 123-45-67» — их разбирает состояние
  анкеты, а не текст;
- ввод с `!` и `/` фильтр не смотрит вовсе: это служебные команды, они
  разбираются раньше, и не-администратору честно отвечают «Не понимаю 🙂»
  тоже без модели;
- аббревиатуры пропускаем: «ООО», «СССР», «СПб», «ДК» — там нет гласных,
  но к делу они относятся;
- слова с `ь`/`ъ` внутри не считаем мусором: это окончания и приставки;
- смешанный текст (кириллица + латиница) не переводим: там названия, e-mail,
  «ок» внутри фразы.

Фильтр стоит **только в свободном диалоге**. Анкета (имя, город, телефон,
почта), вопрос организатору и служебные команды его не проходят: там ввод
не разбирается по смыслу, и отсечение сломало бы заявку.
